# D-0005: Adversarial revision as a first-class verification step

Date: 2026-11-11
Reversibility: easy

## Context
The owner asked that testing include adversarial revision: an attacker mindset,
property-based testing (rules, not cases) and fuzzing at scale. The kit shipped
confirmation-shaped verification (tests + functional run + logical refutation).

## Decision
Adopt it in `verify` §3 and the `brainloom/verifier` mandate, scaled to the input
surface: property invariants over hundreds of seeded random inputs; fuzzing of
trust boundaries with malformed inputs at scale; crash/hang/invariant-break =
finding (FAIL for the verifier). No input surface → declared skip, never a
silent drop. Seeds and counts go in the evidence. No hard numeric minimums in
the skill text — the dry run showed the wording already yields real execution.

## Alternatives considered
- Hard minimums (N invariants, M fuzz cases) in the skill text: rejected — they
  invite gaming the number instead of attacking the surface.
- Separate `adversarial` skill: rejected — verification is one flow; splitting
  it risks the step being skipped when verify is loaded.
